## 1. Customer #2 (C:-only PC) — frozen "Backing up database…" splash

**Symptom**: New customer's app hung on the startup backup splash for ~1 hour.

**Root cause**: Their `appsettings.json` had `BackupPath` on `D:\…` (copied from the standard
install template), but the PC had **no D: partition**. `Directory.CreateDirectory("D:\…")`
threw, and the backup retry loop waited **30 min between each of 3 attempts** → ~1h frozen splash.

**Immediate fix (live)**: edited their `appsettings.json` `BackupPath` to a C: path.

**Code fix** (`BackupService.cs`):
- `DriveExists()` check — if `BackupPath`'s drive doesn't exist, auto-fall-back to
  `%LocalAppData%\AccessControlPro\Backups` (always on the system drive) and log it.
- Fail-fast retry — the 30-min delay now only applies to transient errors
  (`SqlException`/`TimeoutException`); path/permission errors break immediately.

(Subscription-plans "error" the same customer mentioned was never reproduced with a real
message; code + schema both check out. Left pending a concrete error string if it recurs.)

## 2. Basmia crash-recovery bundle (2026-06-07) — diagnosed

Bundle: `basmia\20260607-133149.zip` (downloaded from SuperAdmin → Diagnostics). All files
verified internally consistent and 100% Basmia (cloud slug "DRAG" = `gymcloud_drag`, single
device `192.168.1.150`, Iraqi data).

**Verdict: NOT a software crash.**
- The bundle contains **no `crash_log.txt`** → no exception was logged.
- `startup_log.txt` June 7 16:37 launch: *"Previous session: KILLED OR CRASHED — process 2688
  … stopped without clean shutdown."* Per the app's own rule, no crash_log entry = force-kill
  / power-loss / Task-Manager close.
- Backups healthy (323 MB twice daily to `D:\Backups` — **Basmia's PC does have a D: drive**),
  cloud sync healthy, network self-test green.

**What actually happened**: process 2688 ran ~20h; working set crept to **700–706 MB**. The
receptionist almost certainly force-closed the "heavy" app (~16:30) and reopened at 16:37 →
that relaunch fired the crash-recovery bundle.

**Real bug found in `memory_log`**:
```
16:13 [error] working set high (706 MB) — forcing Gen2 compacting GC
16:13 [error] monitor failed: AggressiveGC requires setting the blocking parameter to true
```
The >700 MB emergency GC — the safety net against the original Basmia OOM — was calling
`GC.Collect(2, GCCollectionMode.Aggressive, blocking: false, …)`, which **throws every time**
because `Aggressive` requires `blocking: true`. The net never worked.

## 3. v4.6.0 — four fixes shipped

Commit `527d626` on `feature/pwa-cloud`.

1. **`BackupService.cs`** — drive self-heal + fail-fast retry (fix #1 above).
2. **`App.xaml.cs:896`** — emergency GC `blocking: false → true`. (Line 118's OOM-cascade path
   was already correct; only the 700 MB monitor path was broken.)
3. **`App.xaml.cs`** — restart-recommended nudge now also fires on sustained **>750 MB** working
   set, not only 5-day uptime. Converts the force-kill cycle into a graceful restart (resets
   memory to ~180 MB, preserves clean shutdown, kills the false crash-recovery noise). New
   field `_lastWorkingSetMb` is sampled by the memory monitor.
4. **`DatabaseMigrator.cs`** — idempotent `ALTER DATABASE CURRENT SET RECOVERY SIMPLE` on every
   launch. Replaces the manual `tuneup.sql` step → no customer (incl. #3) can hit
   transaction-log-full. (Basmia's long-pending SIMPLE-recovery item is now automatic.)

Version bumped 4.5.0 → 4.6.0 across WPF/Admin/POS.

## 7. v4.6.2 — auto-update Updater self-overwrite fix (FIRST real end-to-end test)

Before shipping 4.6.1 to customer #2, tested the auto-update flow end-to-end for the **first
time ever** on the demo install (`D:\AccessControlPro-Demo`, 4.5.0 → 4.6.1). Check, bilingual
prompt, Arabic notes, download, SHA verify, pre-update backup all worked — then the **Updater
failed** at the file swap:

> The process cannot access the file `Updater.exe` because it is being used by another process.

**Root cause**: the Updater ships *inside* the release ZIP and runs *from the install folder*,
so extracting the new `Updater.exe` over the running one locks → whole update aborts. (Rollback
safety net worked; `_rollback\` had the old version.)

**Fix** (`tools/Updater/Program.cs`): the Updater now copies itself to `%TEMP%\acp_updater_<pid>\`
and **relaunches from there** (with a `--relocated` sentinel to avoid a loop) before the swap, so
it can freely overwrite the install-folder `Updater.exe`. **Re-tested on the demo: 4.5.0 → 4.6.1
completed cleanly** (570 files written, app relaunched as 4.6.1, no lock error).

**Shipped as v4.6.2** (commit `f73d926`), live + verified on the VPS:
- ZIP `AccessControlPro-v4.6.2.zip` — 110,555,478 bytes
- SHA-256: `1AF176D6E5210D0D68CC798B42D090A853BA5F36D41D0B38171B68D082A2D46F`
- `latest.json` + `/api/version/latest` both serve **4.6.2**; EN+AR notes verified.

**IMPORTANT — existing installs carry the OLD buggy updater** (the buggy updater can't deliver
its own fix via auto-update). To get them onto the fixed updater, ONE of:
- drop the fixed `Updater.exe` into their folder once (single file — `tools/Updater/bin/Release/
  net8.0-windows/win-x86/publish/Updater.exe`), *then* let them auto-update to 4.6.2; OR
- do a full manual install of the 4.6.2 ZIP (carries the fixed updater).
After that one step, all future auto-updates work permanently. Applies to **Basmia** (her pending
manual install covers it) and **customer #2** (copy one file). Fresh installs of 4.6.2 are fine
from day one.
