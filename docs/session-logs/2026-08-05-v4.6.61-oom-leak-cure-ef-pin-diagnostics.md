## Why this release exists

The 4.6.59 auto heap-histogram (`heap_log.txt`) finally **named the leak**. Reviewing the
SuperAdmin diagnostic bundles (harith / Power SEVERE):

- **Power heap dump = 631 MB in `System.Byte[]` (34,818 arrays).**

That is the smoking gun for the chronic 32-bit `OutOfMemoryException` that has been crashing
busy gyms for months. Root cause traced to **`ExpiryMonitorService`**.

Four fixes shipped together ("سويهم كلهم ما دام لكينا العله وين"):

### 1. THE OOM CURE — `ExpiryMonitorService` photo churn  ⭐
`CheckAndExpireAsync()` ran **every ~10 seconds** and loaded **every player entity WITH its full
JPEG `PhotoData` byte[]** (tracked, no projection) just to count who is expired. ~1,000 players ×
~108 KB photo × 6×/min ≈ **~108 MB/min of dead photo byte[]** churned through the 32-bit heap/LOH →
fragmentation → `OutOfMemoryException` at the WPF render layer.

**Fix:** new photo-free, `AsNoTracking` projection on the hot path.
- `IEmployeeRepository.GetExpiryMonitorRowsAsync()` → `IReadOnlyList<ExpiryMonitorRow>`
  (`ExpiryMonitorRow` record = Id, FullNameEn, IsFrozen, EndDate, MaxVisits, UsedVisits,
  HasActiveSyncedCard — **no PhotoData**).
- `EmployeeRepository`: `db.Employees.AsNoTracking().Select(... e.AccessCards.Any(c => c.IsActive && c.IsSyncedToDevice))`.
- `ExpiryMonitorService` rewritten to iterate the lightweight rows and only COUNT/log. The
  hardware itself still enforces expiry (effectiveTimes countdown + ValidTo date), so no device
  writes were lost. `BuildDeviceInfo` + several injected deps are now unused (warnings, harmless).

### 2. Fursan POS startup crash — EF-Core version drift  ⭐
Fursan's POS threw `FileNotFoundException: Microsoft.EntityFrameworkCore 8.0.29`. Cause: the csprojs
referenced EF Core as **`8.0.*`** (floats to 8.0.29 at restore time) while the shipped payload DLL
was **8.0.28**. When `dotnet publish` regenerated a `deps.json` listing **8.0.29** but the folder
carried the **8.0.28** DLL, the runtime manifest lookup failed → crash. Confirmed: v4.6.60 payload
had DLL 8.0.28 but `AccessControlPro.WPF.deps.json` said `EntityFrameworkCore/8.0.29`.

**Fix — pin at source** so a build can never drift again:
- `Infrastructure.csproj`: `EntityFrameworkCore.SqlServer` + `.Tools` → `8.0.28`
- `WPF.csproj`: `EntityFrameworkCore.Design` → `8.0.28`
- Restored/rebuilt → all three `deps.json` now say **8.0.28**, matching the DLL. In staging the
  **deps.json files were refreshed too** (not just the 7 app DLLs) — that was the actual bug carrier.

### 3. Diagnostics bundle bloat
`DiagnosticsService.EnumerateLogFiles` slurped every `*log*.txt` — hundreds of legacy
`auth_log_*` files bloated bundles. Now: excludes any filename containing "legacy", caps the
"extra logs" set at the **15 most-recent**, and always includes the priority files
(`heap_log.txt`, `memory_log.txt`, session/rolling logs).

### 4. Memory monitor off the UI thread
The ws sampler + heap-histogram trigger ran on a `DispatcherTimer` — unreliable exactly when it
matters most (UI frozen at high memory). Moved to a `System.Threading.Timer` → new static
`App.SampleMemory()` on a background thread: logs ws/priv/heap/GC/windows to `memory_log.txt`,
reads window count non-blocking via `Dispatcher.InvokeAsync` + `op.Wait(1500ms)` (logs `windows=-1`
if the UI is busy), fires the ClrMD histogram inline at `600<ws<1500` (hourly throttle,
`_heapCaptureRunning` Interlocked guard), and force-compacts GC at `ws>700` — now off-UI, no freeze.
