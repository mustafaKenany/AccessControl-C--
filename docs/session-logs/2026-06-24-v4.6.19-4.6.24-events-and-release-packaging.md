## Bug 1 — Event-log mislabeling (reported on noamani)
Symptom: events showed "Alarm" with detail "Card Open", and non-card rows all said "Card Open".
Root causes (fetched-records path):
- `SdkRecordTypeToDomain` (in `AccessControlSdkWrapper.cs`) only swapped Card/Button (0↔1).
  SDK getRecord indices are `System=4, Alarm=5`; Domain enum is `Alarm=4, System=5` → System
  events were stored as Domain.Alarm. (noamani had 404 such.) Added 4↔5 swap.
- `GetEventDescription` (in `AccessEventService.cs`) derived text only from the controller's
  status field (CSV `parts[4]`, almost always `1`), which only carries a card outcome for CARD
  records. Made it record-type-aware: card outcomes for Card only; other types described by type.
- Live-monitor `WatchEvent` path uses a different decompiled source and was left untouched.
- Historical rows keep their stored (swapped) type until 6-month retention; new events correct.

## Bug 2 — Release-packaging left internal DLLs stale (IMPORTANT)
How releases are assembled: clone the previous staged folder `publish/vX` → overwrite DLLs → zip.
I had been copying ONLY `AccessControlPro.{WPF,Admin,POS}.*`. The internal libraries
(`SDK/Application/Domain/Infrastructure`) had **no `<Version>`** (defaulted 1.0.0.0) and were
never re-copied → frozen at the 4.6.18 base bytes through 4.6.19–4.6.23.
Consequences:
1. Every machine ran a **mixed build** (app DLLs new, internals 4.6.18). This is exactly what
   noamani's diagnostics bundle showed (WPF=4.6.22 / Application.dll=4.6.18) — NOT an install fault.
2. The **4.6.23 event fix lives in SDK.dll + Application.dll → it never shipped**.
Detected by hashing staged-vs-fresh DLLs (fresh SDK `789f855bb5` ≠ shipped `4637a6c003`).

**Fix (4.6.24):** `src/Directory.Build.props` is the single version source for all 7 projects
(per-csproj `<Version>` removed from WPF/Admin/POS). **Packaging rule going forward: copy EVERY
`AccessControlPro.*.dll` from `…/WPF/bin/Release/net8.0-windows/win-x86/`, plus each app's
exe/deps/runtimeconfig.** Native hardware SDK (`CareaIfc.dll/CtrlEx.dll/DataTool.dll`) are
byte-identical across all 4.6.x (verified) → packaging leaves them as-is; updates can't break the
gate. (A transient `_wpftmp` NETSDK1047 error may appear on the first multi-project build after a
props change — a clean WPF rebuild succeeds.)
