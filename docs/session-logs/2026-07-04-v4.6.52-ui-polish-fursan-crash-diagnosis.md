6. **Assign-card sync-dot fix.** Repro: assign a card via the Assign-Card dialog (device ticked) → "success" → the gate-sync dot stayed RED. Cause: the VM synced `Cards.LastOrDefault()`, which — if the member had another card record — pushed a stale card and left the newly-assigned one un-synced. Fix: sync the card matching `dialog.CardNumber`. (The whole sync-status mechanism is otherwise correct: `SyncCardToDeviceAsync` sets `IsSyncedToDevice=true` on push success, saves it, and the list reloads → green; red = genuinely not on the gate.)

## Fleet crash-bundle diagnosis (3 gyms, all "crash-recovery")
Pulled the latest crash bundles from the VPS (`/var/www/gymapp/diagnostics/<GymId>/<ts>.zip`, extracted with `python3` zipfile — no `unzip` on the box) and read `logs/crash_log.txt`. **They were NOT the same error:**
- **classic (18):** `InvalidOperationException: DUPLICATE_PHONE:0` in `EmployeeService.UpdateEmployeeAsync ← EnsureMigrationDefaultsResolvedAsync ← RenewSubscriptionAsync` — migrated members sharing phone "0". **A real code bug.**
- **power (17):** `OutOfMemoryException` then 2× `RetryLimitExceededException` (SQL connection pool exhausted) — the memory-leak class (Basmia incident), the DB errors downstream of the OOM.
- **ALI (14):** no managed exception in the recent bundles (only old benign "Application is being shut down" from June 30) — an unclean/hard exit.

All three underlying fixes had already shipped in **4.6.51** (the `IsBlankPhone` DUPLICATE_PHONE fix + the `DbConnectionHelper.IsConnectionError` chain-walking hardening + the OOM special-casing in the global handler). This session confirmed the diagnosis.

## v4.6.53 — SHIPPED (commit `20ac492`, zip SHA `6CD64E50…70DA`, WPF.dll SHA `C2C9CE84…B998`, mandatory)
Two things: the migrated-Renew correction (operator-verified on Demo) + a set of memory/crash-recovery mitigations that came out of the crash-bundle diagnosis.

1. **correct-inside-Renew for migrated members.** Removed the forced separate-Edit pre-step (`EnsureMigrationDefaultsResolvedAsync` no longer called — now dead code, left in place, delete in a follow-up). The Renew dialog shows an amber **correction panel** (Name En/Ar + Phone, pre-filled, MIG-placeholder phone cleared) **only for a migrated member** (`RenewSubscriptionDialog.IsMigratedCorrection`); the VM saves the corrected name/phone (`UpdateEmployeeAsync`) then renews (replaces "Migrated" + sets dates) — one flow. Name required; phone may stay blank; genuine duplicate-phone → friendly message + abort (no crash). Active migrated untouched.

2. **Memory/crash mitigations (from the 2026-07-05 crash-bundle audit — power(17) is the one genuine OOM/leak crasher):**
   - **Scheduled idle app-restart** to reset the leak baseline — default **16:00 + 23:00** (operator's chosen times), configurable via `appsettings "AppRestartTimes":["16:00","23:00"]` (empty array = off). `_scheduledRestartTimer` (1-min tick) restarts via `RestartApp` ONLY when `IsSafeToRestart()` (no modal window open — "if it's open and OK"); if busy it retries every minute for 30 min, then skips the slot for the day. Clean **app** restart (~5 s), not a machine reboot.
   - **OOM self-heal** — the global `DispatcherUnhandledException` OOM branch counts OOMs; after 3 in a session, `RestartApp("OOM auto-recovery")` at the next safe moment instead of limping into a hard kill.
   - **No more false crash-recovery bundles** — `RestartApp(reason)` + the auto-update handoff now call `LastRunStateTracker.RecordPlannedRestart(...)` before `Environment.Exit`/the Updater's process-kill. Previously the Updater killing the app to swap files left the state at "running" → spurious "crash-recovery" bundle on next launch; now it's "planned_restart". Makes the SuperAdmin crash board trustworthy.
   - **`memory_log.txt` now logs `windows=`** (open-window count) alongside ws/heap/GC — the clearest WPF-leak signal.

**NEXT (leak hunt for power):** now that power runs 4.6.53, pull a day of its `memory_log.txt` from a fresh bundle → whichever of **working-set / managed-heap / window-count** climbs pinpoints native-SDK vs managed vs dialog leak; one heap dump at high memory settles it definitively. Also still-pending cleanup: delete the dead `EnsureMigrationDefaultsResolvedAsync`/`IsMigrationDefault` VM methods.
