**4.6.59 is LIVE** — commit `20f4a59` (pushed to GitHub `feature/pwa-cloud`), zip SHA `E9734DA5403BBBF9B401C576F267D2DE223C70931C8BA4391C22C988C4187007`, size `111040027` (574 files — +3 ClrMD DLLs), mandatory. Built on top of 4.6.58.

## Why
4.6.58 mitigates the 32-bit OOM leak (harith/Power) with a twice-daily PC reboot, but the real cure needs a heap dump to pinpoint the leaking object — and a full 32-bit dump is ~1–2 GB (too big to auto-upload, nginx-limited, and often fails *at* OOM). So instead the app now captures a tiny **managed-heap histogram** (top object types by size+count) into the diagnostics bundle — a few KB that directly names the leak. Operator ("mustafa") proposed sending it via the diagnostics system; this is the refined implementation.

## What shipped
- **`HeapHistogram.CaptureTopTypes()`** (`src/AccessControlPro.WPF/Helpers/HeapHistogram.cs`): ClrMD `DataTarget.CreateSnapshotAndAttach(self)` walks the app's own managed heap, groups by type, writes the top-25 by bytes (with count, total managed heap, ws). Never throws — on failure writes `capture FAILED: <reason>` (itself signal). **Managed-only:** if it stays flat while ws still climbs to the ceiling → the leak is NATIVE (the SDK), which itself narrows the hunt.
- **Trigger 1 (auto):** the existing 10-min memory monitor fires a capture when `ws > 600MB`, throttled to hourly, only in a safe window (`< 1500MB`) so the capture can't tip a 32-bit process over. Runs OFF the UI thread (heap walk ~seconds) via `Task.Run` + an `Interlocked` guard. Writes to **`heap_log.txt`** (name contains "log" → the diagnostics bundler's `*log*.txt` glob auto-includes it). So a crash-recovery bundle carries the pre-crash histograms (heap_log is a rolling 60-day file, persists across sessions).
- **Trigger 2 (on-demand):** `MainWindow.SendDiagnosticsClick` captures a fresh histogram *before* the upload, so a manual "Send Diagnostics" from any gym includes a live snapshot at any memory level (also how it's testable on Demo, which never reaches 600MB).
- **Dependency:** added `Microsoft.Diagnostics.Runtime` (ClrMD 3.1.*, pure-managed). New shipped DLLs: `Microsoft.Diagnostics.Runtime.dll`, `Microsoft.Diagnostics.NETCore.Client.dll`, `System.IO.Pipelines.dll`. **Packaging note:** the release is clone-v(prev)+overwrite-7-DLLs; a NEW dependency also required copying those 3 DLLs in AND overwriting `AccessControlPro.WPF.deps.json` with the fresh build's version. Verified safe: the current shipped deps.json already lists EF-Design (25 refs) whose DLLs are absent and the app runs fine — the "listed-but-absent" pattern is proven, so the fresh deps.json (adds ClrMD chain, keeps EF-Design listed-but-absent) is fine.

## How the leak hunt now works
Once harith/Power update to 4.6.59, their next bundle (auto crash-recovery, or a manual "Send Diagnostics") will contain `heap_log.txt` with the top-types histogram at elevated memory → read it from SuperAdmin, see e.g. "1.2M System.Windows.Media.Visual = 600MB" → fix that leak at the source. No AnyDesk, no multi-GB dump.
