## Fleet diagnostics (2026-07-16, all 9 gyms on 4.6.57) — the reason for this release
Analyzed all 29 diagnostic bundles. **3 gyms genuinely crashing, all the same class:**
- **harith/Aldoor (16) — SEVERE:** 10 bundles, crashing almost daily (07-08→07-16), 8× `OutOfMemoryException` at the WPF composition layer (`DUCE.Channel.SyncFlush`, `MediaContext.CompleteRender`). Often so severe it hard-kills before it can even write a crash entry.
- **Power (17) — SEVERE (chronic):** crash count GROWING across bundles (14→17→19 entries), 12× OOM + SQL pool-timeouts (`AccessEventRepository.DeleteOlderThanAsync`) + unobserved-task AggregateExceptions, all downstream of the OOM.
- **phisphor (13) — moderate:** 3× OOM (WPF binding/render) + one recent kill.
- The rest (noamani, MAW, Classic, O2, basmia) = benign: hard-kills (Windows shutdown / power loss), historical/fixed entries (Classic's `DUPLICATE_PHONE:0` was fixed in 4.6.51), or cosmetic OnExit shutdown-races.

**Root cause = the 32-bit address-space ceiling.** The app is `PlatformTarget x86` / `win-x86` — it *must* be, because the vendor gate SDK DLLs are 32-bit. A 32-bit process is capped at ~2–4 GB of address space **regardless of the 8 GB machine RAM**. The known WPF Visual-tree + native-SDK leak slowly eats that address space; startup is always healthy (~130–180 MB in every bundle) but busy gyms climb to the ceiling over hours → OOM at whatever allocates next (always the renderer). This is why harith + Power (the busiest) crash and the quiet gyms don't. x64 is not an option without x64 vendor DLLs. **Diagnostics gap noted:** bundles only capture the *startup* memory line, not the pre-OOM climb — a heap dump on Power/harith at high memory is still the way to pinpoint the exact leaking object.

## The fixes (operator-directed)
1. **Twice-daily FULL PC REBOOT** (App.xaml.cs). The 4.6.53-era scheduled restart (was app-restart, then OFF-by-default in 4.6.54 to kill the loop) is repurposed to a **full Windows reboot** — clears the native SDK handles too, not just the managed heap. **Default ON at 17:00 + 22:00** (operator's chosen times) via appsettings `"AppRestartTimes":["17:00","22:00"]` (empty array = off). `shutdown /r /t 120` = 2-minute Windows warning (cancelable with `shutdown /a`). **Uptime guard:** skipped if the app has been running < 2h (a fresh process has no leak to clear; also cleanly covers the post-reboot relaunch). Kept the **persisted slot marker** (`%LocalAppData%\AccessControlPro\scheduled_restart.txt`) + `RecordPlannedRestart` → no reboot loop, no false crash bundle. OOM self-heal unchanged (still an app-restart on 3 OOMs).
2. **`EnsureAutoStartOnBoot()`** — registers `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` = the gate app relaunches after the reboot. Called **only when the reboot feature is enabled**. ⚠️ Requires the PC to also have **Windows auto-login** enabled to reach the desktop unattended after reboot.
3. **`ThermalReceipt.PrintToDefault`** wrapped in try/catch — a bad/missing default-printer driver (`NotSupportedException` on ALI GAYAR) now shows a friendly "check the printer" message instead of crashing.

## ⚠️ Ops notes / caveats
- **17:00 is peak hours** — a full PC reboot then takes the gate offline ~1–2 min. The 2-min warning softens it; operator chose these times knowingly. Easy to change via appsettings.
- **Per gym PC: enable Windows auto-login** (`netplwiz` → uncheck "Users must enter a password") or the reboot leaves the machine at the login screen with the gate app not running.
- **Demo protected:** set `"AppRestartTimes": []` in `d:\AccessControlPro-Demo\appsettings.json` so 4.6.58 on the dev PC does NOT reboot it (and doesn't register auto-start). To test the reboot, temporarily set a near-future time there.
- Gyms that had `"AppRestartTimes":[]` from the old 4.6.54 loop-hotfix will have the reboot OFF — remove that override to get the new default.
